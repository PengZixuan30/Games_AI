# 技能(Skills)

[返回 README](../../README.zh-CN.md)

技能（skills）是写给 AI 的**标准作业程序**：一份 Markdown 文件，说明某类任务该按什么步骤做、有哪些必须遵守的约束。与工具的分工是——**工具给 AI 能力，技能给 AI 规程**。

## 1. 它解决什么问题

模型本身知道怎么调用 `modify_custom_tools`，但它不知道你的服务器上"加白名单前必须先确认玩家名拼写"或"删除工程前必须确认工程已认领"。这些规则写在技能文件里，AI 在执行相关任务前读取，就能按你的流程办事，而不是按它自己的猜测。

关键在于**懒加载**：技能正文不会一直占用上下文，只有被读取时才进入对话。所以：

- **技能索引**（`skills.json`）里只放"什么时候该读它"的一句话——这部分**始终**在系统提示里，属于固定开销；
- **技能正文**在你或 AI 判断需要时才读入，读完就留在本轮上下文里。

因此 `description` 写得好不好，直接决定 AI 会不会在对的时机想起这个技能。

## 2. 内置技能

插件自带三个技能文件，AI 在执行对应操作前会自动读取，你不需要注册它们：

| 技能文件 | 内容 |
|---|---|
| `skills_management.md` | 技能文件的读取、写入、修改、删除流程 |
| `custom_tools_management.md` | 安全地读取、编辑、追加自定义工具代码的流程。其中包含一条强制步骤：**在动手写代码之前**先向用户确认需求、参数、权限等级与期望返回值 |
| `mineflayer_bot_guide.md` | 操控 Mineflayer 假人的流程（仅在假人运行时才出现在索引里） |

这三个文件是只读参考，通常不需要你改动。

## 3. 添加自己的技能

技能文件放在：

```
config/games_ai/skills/
```

格式为 Markdown（`.md`）。注册它需要在同目录的 `skills.json` 中添加一条：

```json
[
    {
        "file": "whitelist.md",
        "description": "添加/删除/查询白名单时都应读取此技能文件"
    }
]
```

- **`file`** —— 技能文件名，相对于 `skills` 目录；
- **`description`** —— 展示给 AI 的一句话，说明**何时**应读取它。这是全文最重要的一行：它常驻系统提示，是 AI 判断"要不要读"的唯一依据。

注册后，技能名会出现在 AI 的系统提示中，AI 可用 `read_skills` 工具在执行相关任务前读取全文。

### 怎么写 `description`

| 写法 | 效果 |
|---|---|
| `"白名单相关"` | 太笼统，AI 很难判断触发时机 |
| `"添加/删除/查询白名单时都应读取此技能文件"` | 明确列出**触发动作**，AI 能在正确时机想起它 |
| `"创建/控制/删除假人时必须读取此技能文件"` | 用"必须"表明这是强制流程，比"建议"更能约束模型 |
| `"全物品大宗分类物品清单"` | 不是"何时读"而是"这是什么"——适用于**查询型**技能，AI 需要该清单时自然会读 |

一句话原则：**动作型技能写"何时必须读"，资料型技能写"这是什么"**。

### 技能正文怎么写

正文是给模型的操作规程，不是给人看的文档。经验做法：

- 开头一句话说清**适用范围**（"本技能用于…"）；
- 步骤用有序列表，每步只做一件事；
- 把**不可逆操作**单独列出并要求确认（"删除前必须复述工程名并要求玩家确认"）；
- 写明**失败时怎么办**（"若工具返回权限不足，直接告知玩家所需等级，不要重试"）；
- 提到具体工具时写**工具名**（`modify_custom_tools`），模型能直接对应上。

> [!TIP]
> 技能不必长。一份 20 行的清晰规程，比 200 行的模糊说明更能约束模型行为。

## 4. 让 AI 自己维护技能

AI 有三个工具可以操作技能文件：

| 工具 | 用途 | 权限 |
|---|---|---|
| `write_skills` | 创建或**覆写**技能文件，同时登记到索引（`skills`、`summary`、`content`） | 配置权限 |
| `modify_skills` | 以正则替换**精确修改**已有技能（`old_string`、`new_string`，可选 `summary`） | 配置权限 |
| `delete_skills` | 删除技能文件并从索引移除 | 配置权限 |

配合内置技能 `skills_management.md`，AI 会先读后写；`write_skills` 是覆写语义，所以修改已有技能时应当用 `modify_skills`——这样不会因为一次误写丢掉整份文件。

**实际使用方式**就是直接对 AI 说清楚你要什么，例如：

```
!!ask 帮我写一个技能：以后凡是玩家要求传送，你必须先确认目标玩家在线、
      再复述一次坐标，得到确认后才执行。文件名用 tp_safety.md
```

AI 会先读 `skills_management.md` 了解流程，用 `write_skills` 写入文件并把 `description` 登记进索引。之后你在 `skills.json` 里就能看到它。

## 5. 在自己的 MCDR 插件中注册技能

插件可以在加载时以编程方式注入技能，无需读写磁盘文件：

```python
from games_ai.external_skills_loader import register_skills

def on_load(server, old):
    register_skills(
        file_name="my_skill.md",
        description="执行 XYZ 操作前应读取此技能文件",
        content="""## 我的技能

此技能指导 AI 如何……
- 步骤 1：……
- 步骤 2：……
"""
    )
```

- **`file_name`** —— 技能名，AI 用这个名字调用 `read_skills`；
- **`description`** —— 与 `skills.json` 中的同名字段作用一致；
- **`content`** —— 技能全文。

以这种方式注册的技能与 `skills.json` 里的技能**完全等价**：同样出现在系统提示的可用技能列表中，同样可用 `read_skills` 读取。区别只有一个——它们**只存在于内存中**，插件重载后需要重新注册。

> [!IMPORTANT]
> 若你的插件只注册技能（不注册任何工具），在 GamesAI 执行 `!!gamesai reload` 时它不会自动跟随重载，请使用 `register_self()`；详见[热重载](hot-reload.md#热重载)。

## 6. 技能与工具的关系

| | 工具（tools） | 技能（skills） |
|---|---|---|
| 本质 | 可被调用的函数 | 被读取的说明文档 |
| 何时进入上下文 | 函数**声明**始终在（含参数与说明），返回值在调用后进入 | 索引始终在，**正文**只在 `read_skills` 后进入 |
| 谁生效 | 决定 AI **能做什么** | 决定 AI **该怎么做** |
| 出错后果 | 调不动、执行失败 | AI 按自己的理解行事，结果不可预期 |
| 典型内容 | `modify_custom_tools` | "改动前必须先读文件、先向用户确认" |

实践上两者总是配套：**给能力的工具 + 给规程的技能**。只有工具没有技能，AI 会用工具但流程不受控；只有技能没有工具，AI 知道流程却做不了事。

## 7. 排查

| 现象 | 检查点 |
|---|---|
| AI 从不读某个技能 | `skills.json` 里的 `description` 是否写清了触发时机；文件名是否与磁盘上的 `.md` 完全一致（含大小写） |
| 玩家用 `/技能名` 选择技能时提示"未找到技能文件" | 比较时用的是索引里的 `file` 值；确认扩展名 `.md` 与文件名拼写 |
| 改了技能正文但 AI 行为没变 | 技能正文是**每次读取时**才载入的，改完直接生效；若改的是 `skills.json` 索引，需要 `!!gamesai reload` |
| 怀疑技能没被读进上下文 | 开 `!!gamesai debug`，`read_skills` 的调用与结果都会在日志里；`!!ask context` 也能看到上下文随之增长 |
